# Eva Tarot

A light, mobile-first tarot conversation app. React 19, TypeScript, Tailwind CSS, Lucide, Vite, WebLLM and a PWA service worker.

Last updated: 22 October 2026.

## What works

- Chat-first home: ordinary messages start without cards. Add cards or start a new spread inside the same conversation, with 1, 3, 5 and 10-card choices. New spreads use the latest question and receive a full reading; editing an earlier question preserves its own cards.
- Complete 78-card deck: Fool #1–World #22, Wands #23–36, Cups #37–50, Swords #51–64, Pentacles #65–78. Each suit is Ace through King. Existing internal Major Arcana IDs remain unchanged.
- Suggested spreads based on the question, with 1, 3, 5 and 10-card choices. Suggestions are transparent local rules; the actual interpretation is generated by a language model.
- One-tap random draws, optional manual selection, and searchable numbered card library. Artwork is public-domain Rider–Waite–Smith, not licensed Gilded Tarot artwork. See `public/cards/ATTRIBUTION.md`.
- Online AI is the default reader: no model download or WebGPU is needed. With an active provider, the server interprets the latest question, original context, feelings and corrections using canonical card guidance. Initial readings explain meaning, strengths, difficulties, advice and a clear direction in connected everyday paragraphs for each card. Follow-ups use the existing conversation instead of repeating the spread. Provider or network failures offer an honest retry; they never silently become preset text.
- Optional on-device Qwen3/WebLLM remains available through Reader options. It is experimental and can exceed a phone's GPU or memory limits. It never starts or downloads automatically. Choosing it retains private local processing until the user explicitly approves moving the conversation online.
- Past-reading title and notes editing. Revising a question makes a new version with the same cards or a fresh spread, retaining the original in History.
- Profile-photo uploads, IndexedDB autosave, migration from earlier storage, full history/search, calendar activity and future intentions, and validated JSON export/import. Conflicting backup conversations are retained as imported copies; calendar note variants are combined without overwriting current notes. Oversized conflicts reject the import atomically.
- English and Vietnamese primary interfaces and card content, plus ten additional languages for core controls. Both readers are instructed to use the selected language; quality varies.

## Online reading and privacy

The first online request explains that the current question, relevant earlier conversation and selected cards are sent to Eva Tarot's server and its AI provider. Older or on-device conversations require explicit approval before being sent online. Choosing on-device reading again marks the conversation private, including an unanswered question that survives a browser crash. Cancelling online approval keeps the saved question without sending it.

Profiles, photos, calendar notes and other conversations are not part of a reading request. The journal still saves on the current device; server inference does not create a cloud account or synchronize history. Provider data handling follows its policies, so the online reader does not claim that messages stay only on the device. Optional browser speech recognition may use the browser vendor's speech service.

The app commits journal changes before starting either reader. Stop cancels the current online request in the client; the provider may already have processed it. Retries reuse the same question and cards. Interrupted requests remain visible after reload. Invalid, missing or other-device reading links show recovery actions rather than an empty home screen or a silent failure. A render-error boundary offers reload/home without clearing stored data.

## Optional on-device AI and limits

Open **Reader options** and deliberately choose the experimental on-device reader. Light (Qwen3-0.6B, about 360 MB) is the smaller model. Detailed (Qwen3-1.7B, about 1 GB) needs more memory. Runtime assets are additional. A WebGPU-capable browser with shader-f16 and sufficient memory is required; some phones can reload or terminate the page despite reporting WebGPU support. The online reader avoids this GPU workload. Model assets are cached by WebLLM; normal browser storage eviction can remove them.

The app waits for the latest journal changes to commit before loading the reader or starting a reply. A failed or timed-out save blocks startup, and cancelling while that save is pending prevents a later reader start without cancelling the journal write. For uncached downloads, a usable browser storage estimate must show room for the model estimate, a 15% allowance and a 64 MiB journal reserve. Loading can proceed if the browser cannot supply an estimate. The app also requests persistent storage; browser denial is nonfatal, and estimates cannot guarantee against later quota or memory failures.

Where the Web Locks API is available, only one tab on the same origin can hold a private reader at a time. Another tab receives a message to close the existing reader tab. The reader worker and its lock are released on page exit (`pagehide`) and development hot reload. These guards reduce resource conflicts; they do not establish that the previously observed WebGPU failure is resolved on every device.

Only when the on-device reader is selected, model inference runs in a dedicated worker without sending chat text to the app server or an AI provider. Its model assets are fetched from Hugging Face and MLC. Switching to online processing requires disclosure and approval. Optional cloud backup, if separately configured and enabled, sends saved data to that service.

This is a small local model, not ChatGPT. It can misunderstand questions or produce inaccurate interpretations. It is prompted to be practical, candid and specific, acknowledge uncertainty, avoid flattery, and avoid claiming real human experience, fixed outcomes, diagnoses or knowledge of another person's private thoughts. Ten-card/long conversations use bounded excerpts of earlier user context and recent dialogue; all conversation history remains stored even when only a recent portion fits the model.

The local runtime uses an 8,192-token context, a conservative 5,400 UTF-8 byte prompt budget, and reply caps up to 2,560 tokens. Unsupported browsers receive an explicit compatibility message and an online-reader option. Saved card meanings are explicitly labelled as references; canned text is never silently substituted for AI. Reference notes include **Reflect on my situation** to request a personalized response from the chosen reader.

References: [WebLLM](https://webllm.mlc.ai/docs/user/basic_usage.html), [Qwen3-1.7B](https://huggingface.co/Qwen/Qwen3-1.7B), [Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B), [MLC model files](https://huggingface.co/mlc-ai/Qwen3-0.6B-q4f16_1-MLC/tree/main). Runtime and model are Apache 2.0 licensed.

## Run

```sh
npm ci
npm run dev
npm run build
npm test
npm start
```

Node 24 is expected. The built-in server defaults to port 3001. Copy `.env.example` to `.env` and configure a server-side provider for online requests; `npm run dev` runs Vite and the API together. Vite alone supports only the optional on-device reader. Keep private `.env*` files out of source archives.

## Saving and the new address

The live public address is **https://evatarot.xyz**; check TESTING.md for deployment verification and remaining browser-test limits. The existing Vercel project identity remains `evara` to preserve deployment configuration.

Browser storage is isolated by origin. On either old **evara-omega.vercel.app** or **evatarot.vercel.app** address, **Move my saved data** opens the new address and transfers a validated backup via `postMessage`. Both windows verify exact origin, window identity and a per-transfer nonce. No journal contents are put into a URL or sent to a server. Success is acknowledged only after persistence commits. Existing wallet access moves with the backup after a durable storage readback; a different destination wallet is preserved and reported as a partial transfer. The old copy is retained. JSON export/import is the fallback if the browser blocks the new window.

Data is saved locally, not a cross-device account. Browser deletion/eviction can still remove it; keep exported backups. Photo uploads are converted locally to a centered 256px JPEG. Revised questions retain their source reading via `revisedFrom`.

Backup import is additive and commits against the latest IndexedDB snapshot in one transaction. Existing profile values are retained, conflicting conversations become linked imported copies, and differing calendar notes are combined. Edits in another tab or made while an import is saving are reconciled; invalid or oversized combined notes reject the whole import without changing stored data. Success is shown only after the import commits.

The save indicator reports **Saving…**, **Saved on this device**, or **Saving needs attention** from actual persistence state. A successful bookmark or profile edit is not itself proof that storage has committed. Write failures keep edits available in the open app and offer retry/export actions.

If the primary journal database cannot open or be read, the app pauses on a recovery screen instead of showing an empty legacy-storage fallback as a fresh journal. Retry reopens the existing database; it does not replace it with an empty snapshot. Export is offered when data is available in memory. The localStorage fallback is used only when IndexedDB is unavailable, and unreadable fallback data also requires recovery. These protections do not recover data that was already removed or prove that previously missing history still exists.

## Hosted AI configuration

`/api/reading` requires `HOSTED_AI_ENABLED=true` and a provider. `OPENAI_API_KEY` takes precedence over `AI_GATEWAY_API_KEY`; on Vercel, `AI_GATEWAY_ENABLED=true` enables a fresh platform OIDC token per request without copying credentials into the client. The default hosted model is `openai/gpt-4.1` through Gateway (`gpt-4.1` for direct OpenAI), selected after live Vietnamese editorial comparisons. It costs more per reading than the previous mini model; the existing project budget and request/output limits remain unchanged. Override with `AI_GATEWAY_MODEL` or `OPENAI_MODEL` as appropriate. Missing configuration, billing rejection, timeout and incomplete answers return explicit errors. `/api/health` confirms configuration only; a successful real reading is required to verify billing and inference. Never expose secrets through `VITE_` variables.

Readings use familiar language and examples tied to the conversation. Vietnamese first readings receive native-language writing instructions and retain all five card sections. The server supplies canonical symbolism, strengths and risks, then generates advice from the user's circumstances instead of feeding fixed card exercises. Follow-up clarifications stay brief. These instructions guide model output; they do not guarantee perfect wording or factual inferences. Saved answers are retained as written; new replies use the updated style.

The production project has a Vercel WAF rule limiting `/api/reading` to 20 requests per 10 minutes per IP, in addition to the instance-local server throttle. Vercel counts WAF limits per region; these are not per-user account quotas. The existing Gateway project budget is $5 without automatic refresh. Exhausted credits or an unmet account verification requirement stop online responses; the app keeps the conversation available for retry. Check TESTING.md for the latest live-provider result.

## Optional cloud backup

The dedicated Eva Tarot Supabase project is provisioned in Singapore after approval of its $10/month cost. The journal Edge Function supports optional private device backups; users must explicitly enable it. All journal and commerce tables deny direct browser access. Both old Vercel origins and the new domain are allowlisted. A device backup is not an email account or cross-device sync.

## Pricing, payments and owner dashboard

The public landing page is at `/`, the reader at `/#chat`, pricing at `/pricing`, donations at `/support`, and the owner dashboard at `/admin`. Visiting pricing preserves the current reader and draft, including the return route across a same-tab pricing reload. A typed insufficient-credit response opens a dismissible in-chat sheet with current catalog prices; returning after payment never submits a reading automatically. The composer shows the server balance and Daily Card shows the normal online reply cost. PWA installation starts directly in chat.

New wallets receive one free AI reply. Active packages provide 1 / 3 / 5 completed replies for 25,000 / 60,000 / 95,000 VND. One credit covers any card count; follow-up replies cost another credit. The source-price consultation, Lenormand and astrology services are retained as inactive CMS records until the owner explicitly configures and activates them.

Orders use immutable server price snapshots and unique transfer references. Reporting a transfer does not confirm payment. An approved owner must match the bank statement before confirming; the transaction grants credits once, even if confirmation is retried. Donations add no credits. While the pricing page is visible and online, pending orders refresh every 15 seconds, with error backoff, an automatic-check limit, a last-checked timestamp and manual refresh. Order mutation invalidates older in-flight reads. Wallets use private browser capabilities; contact emails do not recover wallets. Clearing site data loses access unless the capability has been transferred.

The reading server reserves credits before inference, refunds failures, and keeps successful results in an AES-GCM encrypted retry cache for 15 minutes. The browser retains a hashed request reference so a lost response can be recovered without a second charge. Longer interruptions can exceed the cache window. Private reading text is not included in analytics. Dashboard metrics are recorded page views, completed replies and verified payments, not claimed unique audience estimates.

Owner access uses Supabase Auth with verified email and a service-side allowlist. New owners must be provisioned separately; contact emails and user metadata never grant admin access. Supabase's built-in email is restricted to organization members. Configure custom SMTP before relying on magic links to other addresses. Do not bypass verification or put credentials in frontend variables.

`supabase/commerce-schema.sql` is the reusable schema; the CLI-generated launch migration also includes private journal tables and the approved trial policy. Provision the owner allowlist separately from versioned source. For the internal reading bridge, generate a random 64-hex `EVA_COMMERCE_INTERNAL_KEY`, put only its SHA-256 hash in `eva_server_credentials` under `reading-api`, and set the raw secret only in the Vercel server environment. Public clients use only the publishable key. Edge functions perform their own capability/admin authentication with `verify_jwt=false`.

## Deploy

Source: [operatoruplift/eva-tarot](https://github.com/operatoruplift/eva-tarot). GitHub CI installs the lockfile with Node 24, runs the full test suite and builds the application. Deployment remains an explicit Vercel action; a GitHub-to-Vercel integration has not been verified.

```sh
npm run build
npm test
npx vercel@latest --prod --yes --scope operatoruplift
npx vercel@latest alias set <ready-deployment-url> evatarot.vercel.app --scope operatoruplift
```

Verify both public aliases, manifest, bundles, all 78 card images, online disclosure, a real hosted reply, reload persistence and reading-link recovery. On-device checks apply only to that optional mode. The service worker caches public app/card assets, never chat API responses or private journal data. Model caching is managed separately by WebLLM.

## Customer recovery preparation — 22 October 2026

Email-verified recovery is implemented behind `VITE_CUSTOMER_ACCOUNTS_ENABLED` and the Edge `EVA_ACCOUNT_ENABLED` gates. It remains disabled until Resend domain/SMTP setup and real delivery checks finish. The new vault recovers the existing wallet and private-backup connections; it does not merge wallets, award another trial, or silently upload a journal on sign-in. Separate local namespaces and explicit backup consent preserve guest data and account boundaries. Only successfully synced data (currently up to 1 MB) is recoverable.

The public payment page, catalog and QR metadata omit the recipient’s legal name. A banking app can still resolve the registered account holder. Current SQL seeds were redacted; historical Git commits were not rewritten.

See [account recovery operations](docs/ACCOUNT_RECOVERY_OPERATIONS.md) for email DNS, secure SMTP handoff, feature activation and acceptance checks.
